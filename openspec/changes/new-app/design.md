# Design: new-app

## Context

Предложение [`proposal.md`](./proposal.md) задаёт мотивацию: создать mobile-first PWA для изучения татарского языка по карточкам, разместить её на Vercel и хранить пользовательские изменения локально, без серверной учётной записи. Приложение должно поддерживать обучение свайпами, группы карточек, скрытие встроенных карточек и добавление пользовательских карточек. Для исходного словаря предназначен `cards.ts`; на момент подготовки дизайна файл пуст и формат данных ещё не определён. Переводы фраз также предстоит добавить.

Наблюдаемое поведение определяют capability specs для [`card-catalog`](./specs/card-catalog/spec.md), [`card-groups`](./specs/card-groups/spec.md), [`study-sessions`](./specs/study-sessions/spec.md), [`local-persistence`](./specs/local-persistence/spec.md) и [`progressive-web-app`](./specs/progressive-web-app/spec.md). Этот документ объясняет архитектурные решения, связывающие требования specs; при расхождении specs являются источником истины для пользовательского поведения.

Текущий репозиторий не содержит приложения, сборочной конфигурации или существующей модели данных. Это позволяет выбрать структуру с нуля, но требует заранее определить стабильные идентификаторы и формат локального состояния: после публикации изменения схемы и встроенного набора карточек не должны уничтожать прогресс пользователя.

Основные заинтересованные стороны — изучающий язык пользователь, автор/редактор встроенного набора карточек и разработчик, публикующий статический клиент на Vercel. Ограничения первой версии: один браузерный профиль, отсутствие авторизации, серверной БД и синхронизации между устройствами; приложение должно оставаться пригодным к обучению после первой успешной загрузки без сети.

## Goals / Non-Goals

**Goals:**

- Создать устанавливаемое mobile-first React-приложение, работающее как статический сайт на Vercel и как PWA после первой загрузки.
- Отделить UI и жесты от бизнес-правил учебной сессии, группировки и изменения карточек.
- Использовать типизированный встроенный набор карточек из `cards.ts`, включая татарский текст и перевод слова или фразы.
- Сохранять пользовательские карточки, группы, скрытые карточки, настройки и учебный прогресс в версионируемом локальном хранилище.
- Сохранять пользовательские данные при обновлении приложения и встроенного словаря, насколько это возможно без серверной синхронизации.
- Обеспечить доступный альтернативный способ управления карточкой без свайпа и покрыть доменную логику автоматическими тестами.

**Non-Goals:**

- Аккаунты, облачная синхронизация, совместное использование наборов и серверная база данных.
- Панель администрирования или редактирование встроенного `cards.ts` из интерфейса.
- Автоматический перевод, генерация контента, озвучивание и проверка произношения.
- Гарантия сохранности данных после очистки данных сайта, удаления браузерного профиля или работы в приватном режиме.
- Сложная геймификация и адаптивный алгоритм уровня Anki/FSRS в первой версии.
- Нативные приложения для iOS/Android; PWA остаётся веб-приложением.

## Decisions

### 1. React + TypeScript + Vite как статическое SPA

Приложение создаётся на React и TypeScript с Vite. Оно собирается в статические файлы и разворачивается на Vercel без отдельного runtime-сервера. Для маршрутов SPA добавляется rewrite на `index.html`; бизнес-данные не хранятся в Vercel functions.

Такой стек соответствует запросу на React, даёт быстрый старт, строгую проверку модели карточек и простой статический деплой. TypeScript особенно важен для миграций локального состояния и проверки содержимого `cards.ts`.

Альтернативы: Next.js не выбран, поскольку SSR, server actions и серверная модель данных первой версии не нужны и увеличивают архитектурную поверхность. Create React App не выбран как устаревшая основа для нового проекта. Многостраничное приложение не даёт преимуществ для локального интерактивного сценария.

### 2. Разделение на domain, application, infrastructure и presentation

Код организуется по функциональным областям (`cards`, `groups`, `study`, `settings`), а зависимости внутри них направляются от UI к application-сценариям и далее к чистой domain-модели. Доступ к `localStorage`, PWA API и браузерным событиям находится в infrastructure-адаптерах. React-компоненты не читают и не записывают хранилище напрямую.

Основные сценарии приложения: создать/изменить/удалить пользовательскую карточку, скрыть/вернуть встроенную карточку, создать/переименовать/удалить группу, изменить состав группы, построить учебную сессию, зафиксировать результат ответа и получить следующую карточку. Доменные функции остаются чистыми, а побочные эффекты выполняются репозиториями через узкий интерфейс.

Это сохраняет тестируемость бизнес-правил и позволяет позже заменить `localStorage` на IndexedDB или серверную синхронизацию. Альтернатива — хранить всё в React context/hooks — проще на старте, но быстро смешивает жесты, персистентность и правила обучения. Полноценные Clean Architecture слои с отдельными пакетами не используются: для небольшого клиента достаточно каталогов и границ импортов.

### 3. Встроенные данные неизменяемы, пользовательские данные хранятся как наложение

`cards.ts` экспортирует валидируемый при сборке массив встроенных карточек со стабильными, никогда не переиспользуемыми `id`. Минимальная модель карточки содержит `id`, татарский текст (`front`), перевод (`back`), тип содержимого (`word | phrase`) и необязательные метаданные. UI работает с единой проекцией встроенных и пользовательских карточек, но источники сохраняются раздельно.

В `localStorage` записывается один versioned envelope, например:

```ts
type PersistedStateV1 = {
  schemaVersion: 1;
  customCards: CustomCard[];
  hiddenBuiltinCardIds: string[];
  groups: Group[];
  progressByCardId: Record<string, CardProgress>;
  settings: UserSettings;
};
```

Пользовательские ID создаются через `crypto.randomUUID()` и имеют отдельное пространство имён. Группа содержит свой ID, название и ссылки на card ID, а не копии карточек. Удаление пользовательской карточки удаляет её ссылки из групп и прогресса одной доменной операцией. Скрытие встроенной карточки исключает её из новых сессий, но не удаляет накопленный прогресс; возврат карточки восстанавливает его.

Наложение позволяет обновлять и исправлять встроенный словарь без перезаписи пользовательских данных. Альтернативы: хранить полную объединённую копию набора проще для чтения, но она устаревает после релиза; хранить каждую сущность под отдельным ключом усложняет атомарность и миграции. IndexedDB пока не нужна из-за малого объёма текстовых данных, но интерфейс репозитория оставляет возможность перейти на неё.

### 4. Хранилище имеет явную версию, миграции и защитное восстановление

При запуске infrastructure-слой читает единственный namespaced ключ, проверяет структуру runtime-схемой и последовательно применяет чистые миграции до текущей версии. Запись выполняется после успешного доменного изменения; ошибки квоты или запрета доступа не скрываются, а переводят UI в состояние «изменения не сохранены». До завершения гидратации не показывается пустое состояние, чтобы оно случайно не перезаписало сохранённые данные.

Если JSON повреждён или версия новее поддерживаемой, исходная строка не перезаписывается автоматически. Приложение продолжает работу со встроенными карточками в безопасном режиме и предлагает сброс локальных данных после явного подтверждения. В development/test миграции проверяются на сохранённых fixtures предыдущих версий.

Альтернативы: неверсированное состояние блокирует безопасное развитие схемы; библиотека глобального state management с persistence-плагином сокращает код, но не устраняет необходимость валидации и миграций. Для первой версии достаточно React state/context на уровне приложения и собственного repository adapter; специализированный store добавляется только при измеренной необходимости.

### 5. Учебная сессия — отдельный детерминированный state machine

Сессия создаётся из снимка доступных карточек выбранной группы: скрытые и удалённые карточки исключаются, дубликаты ID удаляются. Состояние содержит очередь, текущий ID, сторону карточки, результаты текущей сессии и признак завершения. Движок принимает семантические команды (`reveal`, `markKnown`, `markLearning`, `undo`), а не координаты жеста.

Presentation-слой преобразует свайп и доступные кнопки/клавиши в одинаковые команды. Это предотвращает зависимость бизнес-логики от конкретной библиотеки жестов и обеспечивает доступность. По `study-sessions` свайп вправо означает «знаю», а влево — «изучаю»; соответствие продублировано видимыми подписями. Порог свайпа учитывает расстояние и скорость, а незавершённый жест возвращает карточку на место.

Для первой версии `CardProgress` хранит счётчики `known`/`learning`, последний результат, время ответа и `dueAt`. Ответ «изучаю» назначает повторение через 10 минут; последовательные ответы «знаю» используют интервалы 1, 3, 7, 14 и 30 дней с ограничением на 30 днях. Просроченные и ещё не изученные карточки имеют приоритет, а карточка с ответом «изучаю» один раз возвращается в текущую сессию после другой карточки, если она доступна. Алгоритм оформлен как заменяемая чистая стратегия. Альтернативы: случайная колода не использует историю обучения; немедленное внедрение SM-2/FSRS потребовало бы дополнительных продуктовых решений о рейтингах и сроках.

### 6. PWA использует app-shell caching и контролируемое обновление

PWA manifest задаёт имя, иконки, theme/background colors, `display: standalone` и корректный `start_url`. Service worker генерируется интеграцией Vite PWA и precache-ит хэшированные ресурсы приложения. Навигация получает app shell; встроенный `cards.ts` входит в bundle. Пользовательское состояние остаётся только в `localStorage` и не помещается в Cache Storage.

Новая версия service worker не перезагружает приложение посреди учебной сессии. UI сообщает о доступном обновлении, а активация и reload происходят по действию пользователя или на безопасном экране. Офлайн-сценарий проверяется после первой онлайн-загрузки; первый визит без сети не поддерживается.

Альтернативы: ручной service worker даёт больше контроля, но повышает риск ошибок кеширования; network-first ухудшает запуск в нестабильной мобильной сети; runtime-кеширование сторонних API не требуется, поскольку внешних API нет.

### 7. Mobile-first UI не делает swipe единственным интерфейсом

Основной экран оптимизируется под узкую ширину, safe-area insets и управление большим пальцем. Анимация карточки использует transform/opacity и уважает `prefers-reduced-motion`. Во время drag блокируется конфликтующий scroll только в области карточки, а вертикальная прокрутка остального экрана сохраняется.

Для каждой свайп-команды существуют подписанные кнопки достаточного touch-размера и клавиатурный эквивалент. Изменение данных выполняется через формы с явной валидацией и подтверждением только для необратимого удаления. Текст не обрезается по фиксированной высоте: татарские фразы и их переводы могут быть длинными.

Альтернативы: gesture-only интерфейс короче визуально, но недоступен части пользователей и плохо обнаруживается. Готовая gesture-библиотека допускается только если она мала, поддерживает Pointer Events и не затрудняет accessibility; сначала оценивается реализация на Pointer Events без новой runtime-зависимости.

### 8. Проверка строится вокруг доменных инвариантов и реального браузера

Unit-тесты покрывают объединение встроенных и пользовательских данных, каскадное удаление, скрытие/возврат, построение очереди, переходы state machine и все миграции. Component-тесты проверяют формы и одинаковый результат жестов и кнопок. Небольшой E2E-набор в мобильном viewport проверяет создание группы и карточки, обучение, reload с восстановлением состояния, offline reload после прогрева PWA и обновление service worker.

В CI обязательны typecheck, lint, unit/component tests и production build. Валидатор исходного набора отклоняет пустые/повторяющиеся ID и пустые стороны карточки. Альтернатива — полагаться на ручное тестирование мобильного UI — не защищает миграции и сохранность данных, которые являются главным риском local-first приложения.

## Risks / Trade-offs

- [Очистка данных браузера безвозвратно удаляет пользовательские карточки и прогресс] → Явно сообщить об этом в настройках; рассмотреть экспорт/импорт JSON отдельным будущим capability, но не выдавать localStorage за резервное копирование.
- [Лимит или запрет `localStorage` приводит к несохранённым изменениям] → Ловить ошибки записи, сохранять последнее подтверждённое состояние в памяти с индикатором ошибки и не обещать сохранение до успешной записи.
- [Изменение или удаление ID во встроенном `cards.ts` осиротит группы и прогресс] → Считать ID публичным контрактом данных, проверять уникальность в CI, а переименования проводить через явную таблицу миграции ID.
- [Повреждённая или несовместимая схема блокирует запуск] → Runtime-валидация, последовательные миграции, fixtures старых версий и безопасный read-only fallback без автоматической перезаписи исходных данных.
- [Service worker оставит устаревший интерфейс или код миграции] → Хэшированные assets, контролируемое обновление, тест upgrade-сценария и отсутствие бесконечного кеширования HTML.
- [Свайпы конфликтуют с прокруткой и недоступны с клавиатуры/assistive technology] → Pointer Events только на поверхности карточки, порог жеста, кнопки и клавиатурные команды с теми же application actions.
- [Простая стратегия повторения может быть менее эффективна, чем доказанные SRS-алгоритмы] → Изолировать стратегию за чистым интерфейсом и собирать только минимальные совместимые данные прогресса; усложнять после уточнения specs.
- [Один JSON-key делает каждую запись пропорциональной всему состоянию] → Это приемлемо для небольшого словаря первой версии; контролировать размер и перейти на IndexedDB через repository interface, если измерения покажут задержки или приближение к квоте.
- [Отсутствие backend упрощает приватность и деплой, но исключает синхронизацию] → Чётко обозначить ограничение; не добавлять скрытую сетевую передачу данных.

## Migration Plan

1. Использовать capability specs как критерии приёмки и уточнить оставшиеся параметры исходного словаря и интервалов повторения до реализации соответствующих модулей.
2. Создать React/TypeScript/Vite приложение, базовые границы модулей и CI-проверки, не изменяя формат пользовательских данных после публичного запуска без миграции.
3. Определить и провалидировать схему `cards.ts`, заполнить исходный набор стабильными ID и переводами фраз.
4. Реализовать domain/application слой и in-memory repository; зафиксировать его поведение unit-тестами.
5. Добавить `localStorage` adapter с envelope версии 1, runtime-валидацией, обработкой ошибок и migration harness.
6. Подключить mobile-first UI, альтернативные свайпам контролы и E2E-сценарии перезагрузки/восстановления.
7. Включить manifest и service worker, проверить installability и offline reload на production preview Vercel.
8. Выпустить preview, проверить на мобильных Safari/Chrome, затем продвинуть тот же проверенный build в production.

Для первого релиза миграция существующих пользовательских данных не требуется, поскольку приложения ещё нет. Для каждого следующего изменения persisted schema сначала добавляется и тестируется последовательная миграция, затем публикуется код. Изменения встроенных ID сопровождаются mapping старого ID на новый.

Rollback выполняется возвратом Vercel deployment на предыдущий build. Поскольку более новый клиент мог уже повысить `schemaVersion`, предыдущий клиент обязан не перезаписывать неизвестную более новую схему; он показывает безопасное состояние и предлагает обновиться. Поэтому откат к версии, не умеющей читать новые данные, восстанавливает доступность встроенной колоды, но не обязательно редактирование пользовательских данных. Изменения схемы должны по возможности быть additive; необратимые преобразования не выполняются без резервной копии исходного envelope.

## Open Questions

- Нужны ли экспорт/импорт или ручная резервная копия до появления облачной синхронизации?
- Каков ожидаемый размер `cards.ts` и нужны ли категории/теги помимо пользовательских групп?
- Требуется ли двуязычный интерфейс приложения или только русскоязычный UI с татарским учебным контентом?
